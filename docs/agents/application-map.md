# Lymic application map

Read this before changing Lymic application behaviour. It is the implementation-facing map; [the project documentation](../README.md) remains the user-facing reference.

## Product boundary

Lymic is a cross-platform Tauri desktop client that **uploads** media from local **Watched Folders** to one **Immich Server**. It discovers and watches **Media Assets**, avoids uploading **Duplicates** already known to Immich, and records durable progress locally.

It is not a bidirectional filesystem mirror: **Synchronization** does not automatically download **Remote Assets** or apply remote deletions or renames locally. A user-initiated **Download** from the Lightbox saves one **Remote Asset**'s original file to a chosen local path; it is separate from **Synchronization**.

The **Virtual Library** ([ADR-0003](../adr/0003-windows-virtual-cloud-library.md)) is a **planned, Windows-only** optional read-only projection of the **Immich Library** into the Windows filesystem via the Windows Cloud Files API (`cldapi.dll`), exposing **Virtual Placeholders** with on-demand **Hydration**. **It is not implemented on `master` or included in current builds** (there is no `cloud_files` module, `lymic-shell-ext` shell extension, Virtual Library IPC command, or Virtual Library UI/persistence in this codebase), and it is unavailable on macOS and Linux. Even as designed in [ADR-0003](../adr/0003-windows-virtual-cloud-library.md), the **Virtual Library** is strictly read-only and separate from **Synchronization**: Explorer delete, move, and write operations are denied so uploads and asset lifecycle remain exclusively in **Watched Folders** and **Synchronization**. Preserve that boundary unless the product decision explicitly changes it.

Use the defined terms in [`GLOSSARY.md`](../../GLOSSARY.md): **Watched Folder**, **Removable Watched Folder**, **Target Album**, **Album Assignment**, **Upload Unit**, **Synchronization**, **Download**, **Virtual Library**, **Virtual Placeholder**, **Hydration**, **Explore Overview**, **Place**, **Place Timeline**, **Memory**, **Memory Timeline**, **Search**, **Search Mode**, **Search Filter**, **Search Results** and **Location**. Target-album behaviour is governed by [ADR-0001](../adr/0001-folder-target-albums.md); removable-volume behaviour is governed by [ADR-0002](../adr/0002-removable-watched-folders.md); the planned read-only Windows Virtual Library design is recorded in [ADR-0003](../adr/0003-windows-virtual-cloud-library.md); Album Timelines and Place Timelines use paginated metadata search ([ADR-0006](../adr/0006-album-timeline-data-source.md), [ADR-0007](../adr/0007-place-timeline-metadata-search.md)); Search requires Immich 3.2 and has two result presentations ([ADR-0008](../adr/0008-search-requires-structured-filter.md), [ADR-0009](../adr/0009-search-results-two-presentations.md)).

## Runtime shape

```text
Svelte 5 UI (src/)
  invoke commands / subscribe to events
        │
        ▼
Tauri command layer (src-tauri/src/commands/)
        │
        ▼
Rust application services
  sync/  watched_folders/  watcher/  immich/  db/  audit/  app/
        │              │        │
        ▼              ▼        ▼
 Immich REST API    local FS   SQLite + native keyring
```

`src-tauri/src/app/mod.rs` is the runtime composition root. It registers every Tauri command, starts background work, creates the tray, and hides (rather than quits) the main window on close.

## Synchronization lifecycle

1. **Discover:** startup, a manual sync, adding a folder, or watcher events produce a scan. Watcher overflow triggers a rescan.
2. **Classify:** the media layer forms an **Upload Unit** from one asset or an allowed live-photo pair and finds an optional XMP sidecar.
3. **Hash:** unchanged files reuse a cached checksum only when current size and mtime match. Others are streamed while hashing.
4. **Check:** checksum batches go to Immich's bulk-upload check; existing assets are not uploaded.
5. **Queue and process:** missing assets are durably enqueued, then streamed as multipart uploads with configured parallelism.
6. **Assign and record:** when a Watched Folder has a Target Album, both uploaded and duplicate remote assets are assigned to it. Queue outcomes, remote IDs, failures, and progress are persisted.

The durable queue is the recovery boundary: `RUNNING`, `PAUSED`, `FAILED`, and `IDLE` live in `sync_jobs`; `PENDING`, `SYNCED`, and `FAILED` entries live in `sync_queue`. The Synchronization lifecycle coordinates job transitions and runner claims. On restart, pending work without a runner is recovered as paused; resume it from the queue rather than scanning folders again.

## Invariants to preserve

- Watched Folder paths are normalized; duplicates and parent/child overlaps are rejected.
- An unavailable folder remains configured and is retried by watcher reconciliation; it is not silently removed.
- Pause is durable and becomes effective at a safe queue boundary. Resume must be safe after restart.
- A Target Album is copied to the queue entry at enqueue time. Never fall back silently to the root library when its album operation fails.
- Persist `remote_id` after upload so an album-assignment retry does not re-upload the asset.
- Credentials (API key and optional Cloudflare Access token) stay in the native keyring, never SQLite, logs, errors, or UI events.
- Server URLs are HTTPS by default. HTTP is allowed only after explicit opt-in for loopback hosts; credentials in URLs, redirects, query strings, and fragments are rejected.
- Upload and hashing I/O stream files; do not introduce full-file buffering.
- Keep Tauri command names and event names/payloads synchronized with their Svelte callers. `sync-event-subscription.ts` is the frontend event contract.

## Boundary contracts

The map controller (`src/lib/controllers/map-controller.svelte.ts`) owns the session marker snapshot; `MapView.svelte` renders it and opens the shared Lightbox. The registered `get_map_markers` command uses `GET /api/map/markers` through the domain-specific map desktop adapter.

### Tauri IPC

Commands are registered in `app/mod.rs`; implementations live in `commands/`. The command groups are `auth`, `albums`, `timeline`, `people`, `places`, `tags`, `memories`, `search` (`commands/search.rs`, `commands/search_suggestions.rs`), `folders`, `sync`, and `settings`. `get_favorites_timeline_buckets` and `get_favorites_timeline_bucket_assets` belong to the timeline surface and supply the Favorites Timeline with favorite buckets and per-bucket Remote Assets. `get_archive_timeline_buckets` and `get_archive_timeline_bucket_assets` (argument `timeBucket`) are the two read-only commands of the Archive Timeline; they mirror the Favorites pair and are routed through `ImmichSession::with_stored_credentials`. `get_trash_timeline_buckets` and `get_trash_timeline_bucket_assets` (argument `timeBucket`) are the two read-only commands of the Trash Timeline, and `restore_trashed_assets` (argument `assetIds`) is the one Immich write it performs; all three are in `commands/timeline.rs` and routed through `ImmichSession::with_stored_credentials`. `get_asset_details` belongs to the timeline surface and supplies the Lightbox with a Remote Asset's original filename, favorite status, and optional EXIF details. `set_asset_favorite` changes a Remote Asset's favorite status. `download_asset` streams a Remote Asset's original file to the user-chosen Download path. `download_archive` retrieves Immich's ZIP archive, opens the native save dialog with Immich's safe suggested filename, and streams it to the selected path. `add_assets_to_album` adds one or more Remote Assets to an existing Album and reports successful and failed assignments. The Explore commands are read-only: `get_places` (`commands/places.rs`) lists Places; `get_place_timeline` (`commands/timeline.rs`, argument `city`) returns a Place's complete Timeline Buckets and assets; `get_memories` (`size`, clamped to 1-100) returns the newest Memories with their assets, and `get_memories_page` (`page`, 1-based, and `size`) returns a `MemoriesPage` for All Memories (both in `commands/memories.rs`). The People section reuses `get_people` and the `get_person_timeline_*` commands; there is no Explore-specific people command. The Tags commands are read-only and routed through `ImmichSession::with_stored_credentials`: `get_tags` (`commands/tags.rs`) lists every Tag as a flat list, and `get_tag_timeline_buckets` (argument `tagId`) and `get_tag_timeline_bucket_assets` (arguments `tagId` and `timeBucket`) in `commands/timeline.rs` supply a Tag Timeline (see [Tags](#tags)). `get_asset_details` also returns the optional `tags` of a Remote Asset for the Lightbox chips. The Search commands are all read-only and routed through `ImmichSession::with_stored_credentials`: `get_search_support`, `get_search_features`, `search_assets`, `search_context_page` (`page`) and `get_search_suggestions` (see [Search](#search)); the Recognized People filter reuses `get_people` and the city filter reuses `get_places`. Shared frontend IPC contracts live in `src/lib/contracts.ts`, and domain-specific adapter interfaces live in `src/lib/tauri/desktop-adapter.ts`. When changing a command, update its contract, domain adapter interface, owning caller (controller or component), and tests in the same change.

The backend emits `sync-progress`, `sync-progress-percent`, `sync-started`, `sync-transfer-stats`, `sync-progress-snapshot`, `sync-paused`, `sync-resumed`, `sync-error`, `log-message`, and `sync-idle`. Keep event names and serialized payloads backward-compatible within the application release.

### Immich

The core API calls are `GET /api/users/me`, `POST /api/assets/bulk-upload-check`, `POST /api/assets`, `GET /api/timeline/buckets`, `GET /api/timeline/bucket` (the Archive Timeline calls both with `visibility=archive`, see [Archive Timeline](#archive-timeline); the Trash Timeline calls both with `isTrashed=true`, see [Trash Timeline](#trash-timeline)), `GET /api/assets/{id}`, `PUT /api/assets/{id}` (favorite status), `POST /api/trash/restore/assets` (Restore, see [Trash Timeline](#trash-timeline)), `GET /api/search/cities` (Places, one Remote Asset per city, `asset.read`; `immich/places.rs`), `POST /api/search/metadata` with `city`, `withExif`, `order=desc`, `page` and `size=1000` (Place Timeline, `asset.read`, ADR-0007), `GET /api/memories?size=N&order=desc` (Memories, `memory.read`; `immich/memory.rs`), `GET /api/tags` (Tags, `tag.read`; `immich/tags.rs`), `GET /api/timeline/buckets` and `GET /api/timeline/bucket` with `size=MONTH` and `tagId` (Tag Timeline, `asset.read`), the optional `tags` of `GET /api/assets/{id}` (Lightbox chips; see [Tags](#tags)), `GET /api/server/version`, `GET /api/server/features`, `POST /api/search/metadata`, `POST /api/search/smart` and `GET /api/search/suggestions` (Search, `asset.read`; see [Search](#search)), `GET /api/assets/{id}/thumbnail`, `GET /api/assets/{id}/original`, `POST /api/download/archive` (ZIP downloads), and `PUT /api/albums/{id}/assets` (album assignment); album behaviour is in `immich/album.rs` and timeline behaviour is in `immich/timeline.rs`. `GET /api/memories` has no offset or page parameter, so `get_memories_page` requests `size = page * pageSize + 1` Memories, drops the earlier pages, and treats the one extra Memory as the sign that a next page exists; paging counts Memories as Immich returns them, before Memories without dated assets (which cannot be shown) are dropped; a Memory's cover is the first asset that appears in its timeline. Memory responses embed their assets with EXIF and are read with a 32 MiB response cap instead of the default cap. Do not use `/api/search/explore`. Requests use `x-api-key`; bulk checks and uploads use the SHA-1/Base64 checksum contract. Changes to endpoints or payloads require checking the supported Immich API contract rather than guessing.

All Places and All Memories have no navigation entry. Back returns to the view the user came from, tracked in `+page.svelte`: `personOrigin` (`people` or `explore`) for a Recognized Person's Photo Timeline, `placeOrigin` (`explore` or `places`) for a Place Timeline, and `memoryOrigin` (`explore` or `all-memories`) for a Memory Timeline. The Back label and the restored scroll position follow the origin; Explore, People, All Places and All Memories each remember their own scroll position, and sign-out resets the origins and positions.

Failure codes are credential-free strings that the controllers classify: `places_*`, `memories_*` and `tags_*` (`*_authentication_required`, `*_permission_denied:<hint>`, `*_unavailable`, `*_invalid_response`); recognized people keep their `recognized_people_*` codes. One classifier (`request-failure.ts`) maps `*_permission_denied:` to the permission-denied state and `*_authentication_required` and `*_unavailable` to the unavailable state for People, Places, Memories, All Memories, Tags, the Archive Timeline and Trash Restore; anything else is a generic error. Search is the one exception: `search-controller.svelte.ts` checks `search_authentication_required` itself before it calls the shared classifier and shows "Immich did not accept the API key, sign in again" (`authentication_required`) instead of the unavailable state, and it checks `search_context_unavailable` first as well (see [Search](#search)). A Place Timeline failure shows the shared timeline load error. Lightbox actions (Favorite, Download, Add to Album) come from the same `remote-asset-actions.svelte.ts` owner as every other timeline.

Required API key permissions: `asset.read` (Places, Place Timelines), `person.read` (People section) and `memory.read` (Memories); thumbnails and the Lightbox continue to need `asset.view`. A key lacking one of them disables only that section. Immich Web's "Recently added" section is deliberately not implemented.

Not verified against a live Immich server:

- The birthday Memory response shape is a guess. `immich/memory.rs` reads the person's name from `data.personName`, falling back to `data.name`; with neither, the birthday Memory gets the date title.
- ADR-0007's same-named-city finding comes from reading Immich's server source, not from a running server, and names no Immich version.
- Memories need a recent Immich release. No minimum version is documented and the Memory response shape has not been checked against several releases; absent optional fields are tolerated.

### Tags

The Tags view lets the user browse the Immich Library by **Tag**. It is read-only against the Immich Library, has no persisted state (nothing in SQLite) and is separate from Synchronization: Lymic never creates, renames, recolours, moves, deletes or assigns Tags, and Synchronization does not apply them. Immich can create Tags from XMP Sidecars when assets are uploaded, so a Synchronization can add Tags even though Lymic never applies them. Navigation shows "Tags" directly after People. Tags are not part of the Explore Overview or the Virtual Library, and the Map View only hosts the Lightbox chips.

#### Back, `tagOrigin` and scroll positions

`+page.svelte` holds one `tagOrigin = { view, top }` (`tag-origin.ts`): the view a Tag Timeline was opened from and its scroll position. `selectTag` records it with `recordTagOrigin`, which overwrites it only when the Tag Timeline is opened from a view other than a Tag Timeline, so Back after hopping from chip to chip returns to where the chain started, not to the previous Tag. It defaults to the Tags view at the top. The origin can be any view, including the sub-views (an Album, Person, Place or Memory Timeline), the Map and the Search Results. Back (`tags_timeline_return`, "Back to {view}") returns there through the shared `returnTo`, which restores the origin's scroll position (timeline views through `scrollRestore`, other views through the content scroll position) and reloads the Tags view if it went stale. A Tag Timeline opened from another Tag Timeline is a new controller (`{#key tagTimeline}`), so it starts at its top. The Tags view keeps its own scroll position (`tagsScrollTop`) like Explore and People. Sign-out resets `tagOrigin`, `tagsScrollTop`, the open Tag Timeline and the Tags controller (tree, expansion choices, stale flag) through `session-controller.svelte.ts` and `resetView`.

#### Refresh

The Tags controller reuses `createExploreListController` (generation guard, offline fallback, classified error, prefix `tags`) and `createRefreshWhenActive` (`refresh-when-active.ts`, shared with the Explore Overview). The tree reloads every time the view is opened. When a Synchronization settles while the Tags view is the open view it reloads at once (`refreshIfActive`, called from `onSyncSettled` in `session-controller.svelte.ts` with `isTagsActive`); when it settles while another view is open the tree is only marked stale and reloads once on return (`refreshIfStale`, called from `returnTo` when the origin is the Tags view). Tags that are already loaded stay visible when a reload fails because the network or server is unavailable (offline notice); a first load that fails shows the error with Retry.

#### Immich requests and errors

- `GET /api/tags` (`immich/tags.rs`, `tag.read`, no pagination): a flat array of `{ id, name, value, parentId?, color? }`. `value` is the full path. An absent or empty `value` falls back to `name`, and an empty `parentId` or `color` counts as absent; unknown fields are ignored. An entry without `id` or `name`, or an unreadable body, is `tags_invalid_response`.
- `GET /api/timeline/buckets?size=MONTH&tagId=<id>` and `GET /api/timeline/bucket?size=MONTH&timeBucket=<bucket>&tagId=<id>` (`immich/timeline.rs`, `asset.read`), as for `personId`. The metadata search `tagIds` filter is deprecated since Immich v3.2.0 and is not used.
- `GET /api/assets/{id}` may include a `tags` array (`immich/client.rs`), read leniently. A missing, null or non-array `tags` means "no Tags" (`None`), never an error. An entry without an `id`, or with neither `name` nor `value`, is dropped; a missing name falls back to the last segment of the path and a missing path to the name; one malformed entry never fails the request.

Failure codes are credential-free and never carry the response body: `tags_authentication_required` (401), `tags_permission_denied:tag.read` (403), `tags_unavailable` (transport failure and any other status) and `tags_invalid_response`, produced by the shared `request_failure_code("tags", status, "tag.read")`. The shared classifier turns them into the permission-denied state, which names `tag.read`, the unavailable state (authentication required and unavailable alike) or a generic error. A Tag Timeline failure is the shared timeline load error and names no permission. Locale keys are `tags_*` and, for the chips, `timeline_info_tags` and `timeline_tag_open`, in every supported language.

#### Permissions

`tag.read` (Tags view), `asset.read` (Tag Timeline) and `asset.view` (thumbnails and Lightbox, as everywhere). A key without `tag.read` disables only the Tags view, which names the permission and offers Retry; Photos, Explore, Search and every other view keep working. The Lightbox chips need no `tag.read`: they come from the asset details the Lightbox loads anyway.

Immich calls as Lymic sends them (browsing needs `asset.read`; thumbnails and the Lightbox continue to need `asset.view`; Restore needs `asset.delete`, observed on v3.4.1):

- `GET /api/timeline/buckets?size=MONTH&isTrashed=true`
- `GET /api/timeline/bucket?size=MONTH&timeBucket=<bucket>&isTrashed=true`

The browse requests carry no `isFavorite`, `visibility`, `isArchived` or `withPartners` parameter. Buckets are sorted newest first, and `isFavorite` comes from the response. Failures of the browse calls are credential-free strings (`Failed to fetch trash timeline buckets: <status>`, `Failed to fetch trash timeline bucket: <status>`, `Invalid ... response`) and show the shared timeline load error. No minimum Immich version is gated, so a server that rejects the filter surfaces as that load error.

Restore validates the IDs (unique and path-safe) and first sends all selected IDs in one request. Observed on Immich v3.4.1 (see below), `count` is the number of requested IDs that exist and are accessible, not the number actually restored (IDs that were already restored count too), and one unknown or unowned ID makes Immich reject the whole request with HTTP 400 and restore nothing, not even the valid IDs. There is no per-asset result. Lymic therefore trusts the batch only when it answers 200 with a `count` equal to the number requested, in which case every asset is out of the trash. If the batch answers 400, or answers 200 with any other `count`, Lymic falls back to one request per asset: 200 with `count` 1 means that asset was restored, and 400 (or any other `count`) means it failed. A single selected asset is never requested twice. A stale ID, for instance one Immich removed permanently after its retention period while the view was open, can thus no longer block the others, and the partial-failure path (`trash_restore_partial`, failed assets staying selected, retry) occurs for real. Individual requests are sequential and idempotent. A 401, 403, 5xx, a transport error or an unreadable body in either phase aborts the whole call with a credential-free code and no partial result, so assets already restored by then stay in the view until it reloads; retrying is safe. The frontend treats every requested asset not named in `restoredAssetIds` as failed. Request-level failures never forward the response body: `trash_restore_authentication_required` (401), `trash_restore_permission_denied:asset.delete` (403, classified by `classifyRequestFailure(…, "trash_restore")`) and `trash_restore_unavailable` (any other status or a transport error). Lymic no longer reads `GET /api/assets/{id}` after a Restore.

#### Immich requests

All Search requests use `x-api-key` and need `asset.read`. The structured `filter` is the only filter mechanism: no flat field (`personIds`, `city`, `takenAfter`, `rating`, `isNotInAlbum`, `page`, `order`) is ever sent, because Immich rejects a request that mixes them with `filter`.

- `GET /api/server/version` (64 KiB cap): `{major, minor, patch, ...}`. The Search is supported when `(major, minor) >= (3, 2)`. Only a "supported" answer is remembered; an unsupported one is asked again with the next Search. Held in memory.
- `GET /api/server/features`: `smartSearch` and `ocr`; a flag the server does not report counts as off. Read once before the first Search and held in memory; a failure leaves the features unknown (everything stays available) and is read again with the next Search.
- `POST /api/search/metadata` (every chronological Search, also a Context Search without text): `{ filter, orderBy: { field: "localDateTime", direction: "desc" }, size: 1000, withExif: true, cursor? }`. Pages follow `assets.nextCursor` until it is empty or 5 000 results are held (`SEARCH_RESULT_LIMIT`); a repeated cursor or an empty page that promises another page is `search_invalid_response`; a failed page fails the whole load. Results are grouped into Timeline Buckets in local time; assets without a usable capture time are omitted. Responses are read with a 32 MiB cap.
- `POST /api/search/smart` (a Context Search with text): `{ query, filter, size: n * 100, withExif: true }` with no `page`. Immich's structured smart search has **no paging**: it rejects `page` next to `filter` and answers without a next page. Page `n` of the relevance presentation therefore asks for the best `n * 100` results (at most 1 000, `CONTEXT_RESULT_LIMIT`, Immich's maximum `size`), keeps the last 100 and offers page `n + 1` only while the answer filled the window. A Context Search shows at most the best 1 000 results: the page that fills the 1 000 window carries `limitReached`, which the controller reports as `truncated` and the results view shows as a notice (`search_context_limit`).
- `GET /api/search/suggestions?type=<country|state|camera-make|camera-model|camera-lens-model>` with optional `make` (models), `country` and `state` narrowing; blank and null suggestions are dropped. Needs `asset.read`. Cities have no suggestion type here: the city filter uses the Explore city listing (`GET /api/search/cities` through `get_places`, names kept exactly as returned).
- The Recognized People filter lists people through `get_people` (`person.read`; named people first, unnamed ones also selectable).

Structured `filter` keys sent, all combined with AND:

| Search input | Key and condition |
| --- | --- |
| Text, Filename | `originalFileName: { like: "%text%" }` |
| Text, Description | `description: { like: "%text%" }` |
| Text, Folder Path | `originalPath: { like: "%text%" }` |
| Text, OCR | `ocr: { matches: "text" }` |
| Text, Context | no key: the text is the `query` of the smart search. Without text a Context Search runs as a filters-only metadata search. |
| Date | `takenAt: { gte, lte }`, either optional; start of the first and end of the last local day as UTC instants |
| Media type | `type: { eq: "IMAGE" }` or `{ eq: "VIDEO" }` |
| Recognized Persons | `personIds: { all: [ids] }` (omitted when none) |
| Favorite | `isFavorite: { eq: true }` |
| Archived option | `visibility: { eq: "archive" }`; **always sent**, as `{ eq: "timeline" }` when the option is off |
| Unfiled | `hasAlbums: { eq: false }` |
| Rating | `rating: { eq: n }`, n from 1 to 5 |
| Camera | `make`, `model`, `lensModel`: `{ eq: value }` with the suggestion exactly as Immich returned it |
| Location | `country`, `state`, `city`: `{ eq: value }`; country and state from suggestions, city from the city listing |
| Always | `trashedAt: { eq: null }`: Trashed Assets are left out (see below) |

The text is trimmed; `%`, `_` and `\` are escaped with a backslash. Immich's `like` already means "contains" (it wraps the value in `%...%` itself), so Lymic's own `%` wrapping is redundant but harmless. A Search with neither text nor any set Search Filter does not run (`canSubmit`).

#### Errors

Credential-free codes, never the response body: `search_authentication_required` (401), `search_permission_denied:asset.read` (403), `search_unavailable` (transport failure and any other status, including a 500 when Immich's machine-learning service is unreachable), `search_invalid_response` (unreadable body, repeated cursor), `search_invalid_request` (a bug: a Context text sent to the chronological command, or a Context page outside 1 to 10) and `search_context_unavailable` (a 400 from `/search/smart` although `smartSearch` was reported on) and `search_context_service_unavailable` (any 5xx from `/search/smart`, which Immich answers when its machine-learning service is unreachable; this replaces `search_unavailable` for that endpoint only). `request_failure_code("search", ...)` maps the three status codes. `classifyFailure` in `search-controller.svelte.ts` turns the codes into `SearchFailure`: it special-cases `search_authentication_required` (a rejected key asks to sign in again, unlike the other sections, where the shared classifier makes it "unavailable") `search_context_unavailable` and `search_context_service_unavailable` (distinct states with their own messages that leave the Search Mode alone), and hands the rest to `classifyRequestFailure(reason, "search")` (permission denied, unavailable, otherwise a generic "unreadable response"). An unsupported server (`search_unsupported` with the required and the detected version) is a state of its own, not an error. A failed first load with results on screen is the offline state: the previous query and results stay visible with Retry. A failed further Context page keeps the pages already shown and offers Retry. Suggestion, city and people failures stay inside their own filter and never fail the Search.

#### Session state, Back and results

- **Session state**: the text, Search Mode, Search Filters, the loaded features and the Search Results live in memory in the Search controller only. They are reset by the clear control and by sign-out (`session-controller.svelte.ts` clears the controller, `+page.svelte` resets the origin) and are never persisted. Context is the default Search Mode; it falls back to Filename when Smart Search is off, and OCR to Filename when OCR is off. Features that arrive after a clear are discarded.
- **Back origin**: `+page.svelte` holds `searchOrigin = { view, top }`, the view the Search was started from (any view, including sub-views such as an Album Timeline) and its scroll position, recorded the first time a Search is submitted outside the `search` view. Refining from the results keeps the original origin. Back (`search_return` label) and the clear control return there; timeline views restore `top` through `scrollRestore`, other views through the content scroll position; Trash is refreshed and Explore refreshes if stale on return. The Archived option's "Open Archive" link switches to the Archive view like its navigation entry, with no Back button, and keeps the Search in memory.
- **Two result presentations**: **chronological** (every Search except one with a Context text): the controller is itself the timeline (Timeline Buckets by local month, Scrubber, at most the 5 000 newest, a notice when cut) and the notice is `truncated`; **relevance** (Context text): `context-results-controller` exposes one pseudo-bucket (`RELEVANCE_BUCKET`) in the Immich ranking order, 100 per page, further pages loaded while scrolling, no Scrubber, and a notice when the 1 000 limit was reached (`truncated` too). A Search that switches presentation clears the other one's results once the new Search has loaded; if it fails offline, the earlier results stay visible and marked offline, and Retry repeats the new Search (`search.results` is what the view shows, `presentation` stays that of the shown results until then). Both reuse the shared `TimelineView`, Lightbox and Remote Asset actions (Favorite, Download, Add to Album).

#### Permissions

`asset.read` is needed for every Search call; the Recognized People filter additionally needs `person.read` (a key without it disables only that filter and names the permission; the Search itself still works); thumbnails and the Lightbox need `asset.view`. Tags can be read since the Tags view (see [Tags](#tags)), but the Search has no Tag filter yet (#227), so the Search itself never needs `tag.read`; the Tag filter will.

#### Verified on live server v3.4.1

Checked on 2026-11-17 by scripted read-only requests (`POST search/metadata`, `POST search/smart`, `GET search/suggestions`, `GET search/cities`, `GET server/features`, `GET server/version`, `GET people`, `GET tags`, `GET albums`) against a local throwaway Immich **v3.4.1** (official Docker compose, `D:\Development\immich-live-check`, seven generated 100-pixel JPEGs: three of them trashed, two archived, two favorites, none rated, none with camera, location, description or recognized text, no people, no Tags, no Albums, and the machine-learning service not running). Nothing was created, edited or deleted. "Source" means read from the server code in the v3.4.1 container image, not observed behaviour. Lymic's tests use a fake server that returns the shapes seen here.

| Assumption | Status | Observed outcome |
| --- | --- | --- |
| Context is Immich's default Search Mode. | CONFIRMED (source) | The Immich web client bundled in the v3.4.1 image starts every search in "smart" unless the user stored another type, and a typed text with that type is the smart search `query`. Not observable through the API. |
| `filter` is accepted and flat fields cannot be mixed with it. | CONFIRMED (v3.4.1) | `filter` works on `search/metadata` and `search/smart`. `city` or `page` next to `filter` is a 400 "Deprecated field ... cannot be combined with filter". |
| The structured `filter` needs Immich 3.2 (cut-off). | NOT VERIFIED | Only 3.4.1 was available. The v3.4.1 OpenAPI spec marks the flat fields "Deprecated v3.2.0", which is the only evidence. `/server/version` answers `{major, minor, patch, prerelease, featureLevel}`; Lymic reads major, minor and patch. |
| Metadata paging: `cursor` / `nextCursor`, `size` up to 1 000. | CONFIRMED (v3.4.1) | `nextCursor` is an opaque string (base64 of `{"offset":n}`), `null` on the last page; a bad cursor is a 400; `size` 1001 is a 400. `total` and `count` are the size of the page, not of the result. |
| Smart search pages with `page`, `size` and `nextPage`. | REFUTED, fixed | `page` with `filter` is a 400, which Lymic showed as "Context unavailable". The structured smart search takes only `size` (1 to 1 000) and (source) answers with `nextPage: null` and no cursor. Fixed: see [Search](#search) and ADR-0009. A successful smart response was not observed (no machine-learning service: the request validates, then answers 500 "Failed to search smart"). |
| Smart search applies the filters before ranking. | CONFIRMED (source), not observed | The structured smart query filters in its `WHERE` clause, joins the embeddings and orders by cosine distance with `LIMIT`, so the best results among the filtered assets are returned. How the vector index behaves with a very selective filter was not observed. |
| `takenAt` takes `gte` / `lte` instants. | CONFIRMED (v3.4.1) | Both bounds are inclusive and compared as instants (an asset taken at 12:00:00Z matched `gte 12:00:00.000Z` and `lte 12:00:00.000Z`, not `gte 12:00:01Z`); a `+02:00` offset is accepted; an empty `takenAt` object is a 400 (Lymic never sends one). The library has no time zone data, so local day versus UTC capture time was not distinguished. |
| `personIds: { all }` means every chosen person appears. | CONFIRMED (source), not observed | An unknown id is accepted and matches nothing; `all: []` is a 400 (Lymic omits it). The server counts the distinct people among the visible faces of an asset and requires all of them. The library has no people. |
| `tagIds: { all }` semantics. | NOT VERIFIED | Tag filter is out of this delivery (#227). The condition is accepted by the server; the test library had no Tags. (The Tags view does not use `tagIds`: it lists Tags with `GET /api/tags` and filters timelines with `tagId`.) |
| Rating `eq` is exact; unrated assets. | PARTLY CONFIRMED (v3.4.1) | `rating: { eq: 3 }` matches nothing among the unrated assets, `eq: null` matches exactly them; 0 and 6 are accepted without error. Source: `eq` is a plain equality on the rating column. No rated asset existed to see an exact positive match. |
| Case sensitivity of `like`. | CONFIRMED (v3.4.1): insensitive | `like` on file name and path ignores case (`%A3%` and `%.JPG` match `a3.jpg`, an upper-case path matches). `eq` on the file name is case-sensitive. Source: `like` is `f_unaccent(col) ilike ('%' || f_unaccent(value) || '%')`, so it is also **accent-insensitive** (`%à3%` matched `a3.jpg`, confirmed) and always means "contains". The description column uses the same predicate (no description existed to observe it). |
| Backslash escaping of `%` and `_`. | PARTLY CONFIRMED (v3.4.1) | Unescaped `%` and `_` are wildcards (`a_.jpg` and `a%.jpg` match `a3.jpg`). A backslash neutralizes them (`a\_.jpg` and `%\%%` match nothing) and a dangling or doubled backslash is no error. That an escaped character matches the literal character was not observed: no name contained `_`, `%` or a backslash. |
| `visibility` default and the Archived option. | REFUTED default, confirmed option | Without `visibility` archived assets are **included**, so Lymic must send it (it does). `visibility eq archive` returns the same set as the Archive Timeline (the one archived live asset); `visibility eq timeline` leaves it out. |
| Trashed Assets are left out by default. | REFUTED, fixed | The structured `filter` returns trashed assets unless asked not to (the flat search and the timeline calls hid them). Fixed: every Search sends `trashedAt: { eq: null }`, which leaves exactly the live assets; see ADR-0008. |
| `hasAlbums: { eq: false }` selects Unfiled Assets. | PARTLY CONFIRMED (v3.4.1) | Accepted; with no Albums in the library `eq false` returns every live asset and `eq true` none. Source: `not exists (select from album_asset)`. No asset was in an Album to see a positive exclusion. |
| `ocr: { matches }`. | PARTLY CONFIRMED (v3.4.1) | Accepted with any text (also `100%_a`); matches nothing in a library without recognized text. Source: word-similarity on the tokenized text, so no wildcards to escape. |
| `country`, `state`, `city`, `make`, `model`, `lensModel` `eq` versus the suggested values (case, whitespace). | NOT VERIFIED | The conditions are accepted, are plain equality on the EXIF columns (source) and `eq: null` matches assets without the value. The library has no camera or location data, so every suggestion list was empty and no value could be compared. |
| Suggestion requests. | PARTLY CONFIRMED (v3.4.1) | All six types (including `city`, which Lymic does not use) and the `make`, `country` and `state` narrowing parameters are accepted and answered `[]`; an unknown type is a 400. Whether narrowing filters as assumed was not observed. |
| API key permissions. | PARTLY CONFIRMED (v3.4.1) | A key with only `asset.read` and `asset.view` can run `search/metadata`, suggestions, `search/cities`, `server/features` and `server/version` and reaches `search/smart` validation; `GET /people` is a 403 "Missing required permission: person.read". A bad key is a 401 "Invalid API key". A key lacking `asset.read` could not be tested without creating one. |
| `features.smartSearch` means Context can run. | REFUTED as a guarantee | The flag was `true` although the machine-learning service was unreachable; `search/smart` then answers 500, which Lymic shows as a Context-specific message about the machine-learning service (not "Context unavailable", which is for a 400, and not the generic "unavailable"). |

Not observed and still open: the 3.2 cut-off on a 3.2 server, `like` escaping of literal `%`, `_` and backslash in real names, case and whitespace of camera and location values, Rating on rated assets, `hasAlbums` on assets in Albums, `personIds` and `tagIds` `all` against real people and Tags, OCR text matching, a successful smart search response (including that filters rank before the limit), and a key lacking `asset.read`. To re-run the check on another server or release: prepare assets with camera and location EXIF, a description, a Rating, one Album, one Recognized Person with two faces, a Tag and a running machine-learning service, replay the requests above with `curl -H "x-api-key: <key>"`, record the result and the Immich version here, and open an issue for anything that differs.
