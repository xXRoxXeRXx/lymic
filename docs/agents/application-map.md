# Lymic application map

Read this before changing Lymic application behaviour. It is the implementation-facing map; [the project documentation](../README.md) remains the user-facing reference.

## Product boundary

Lymic is a cross-platform Tauri desktop client that **uploads** media from local **Watched Folders** to one **Immich Server**. It discovers and watches **Media Assets**, avoids uploading **Duplicates** already known to Immich, and records durable progress locally.

It is not a bidirectional filesystem mirror: **Synchronization** does not automatically download **Remote Assets** or apply remote deletions or renames locally. A user-initiated **Download** from the Lightbox saves one **Remote Asset**'s original file to a chosen local path; it is separate from **Synchronization**. Besides **Restore**, Lymic performs two kinds of user-initiated writes on **Remote Assets**: **Move to Trash**, a confirmed soft delete into the Immich trash from the Lightbox or a timeline multi-selection ([ADR-0011](../adr/0011-move-to-trash-is-a-soft-delete-on-explicit-user-action.md)), and **Archive** and **Unarchive**, which change a **Remote Asset**'s visibility only between `timeline` and `archive`, never to `locked` or `hidden` and never into or out of the trash ([ADR-0012](../adr/0012-archive-and-unarchive-change-only-visibility.md)). Lymic never deletes permanently, never empties the trash and never trashes, archives or unarchives on its own, **Synchronization** never touches any of it, and local files are never touched.

The **Virtual Library** ([ADR-0003](../adr/0003-windows-virtual-cloud-library.md)) is a **planned, Windows-only, Microsoft Store (MSIX) channel-only** optional read-only projection of the **Immich Library** into the Windows filesystem via the Windows Cloud Files API (`cldapi.dll`), exposing **Virtual Placeholders** with on-demand **Hydration**. **Implemented so far** (#266 in progress): its settings section (a persisted enable toggle, `virtual_library_enabled` in `app_settings`, owned by `createVirtualLibraryController` and `commands/virtual_library.rs`, and the root folder) and the Windows adapter tracer bullet `cloud_files` (#278): enabling checks the root for a nested sync root, then registers and connects the sync root, and the projected tree is listed lazily per directory and hydrated on open. Delete and rename vetoes (#279), reconciliation (#280), hydration failure notices (#281) and unregistering (#283) do not exist yet, and nothing in Explorer has been observed (see `docs/virtual-library-verification.md`). The root defaults to `Lymic` inside the Pictures folder resolved through the Windows Known Folder API (`SHGetKnownFolderPath`, never `%USERPROFILE%\Pictures`, behind the `KnownFolders` seam in `virtual_library_root.rs`), is shown in settings and can be changed with the folder picker (`virtual_library_root` in `app_settings`). A Watched Folder may not be inside, equal to or a parent of the root: `watched_folders::register_folder` rejects it (through `FolderPersistence::virtual_library_root`, which calls `virtual_library_root::protected_root` and is `None` while the Virtual Library is unavailable; `commands/virtual_library.rs`, the Tauri adapter, and `watched_folders/` both depend on the domain module `virtual_library_root.rs`, never the other way round), and enabling, or choosing a root that overlaps, is refused with a message naming the Watched Folder. The section exists only when the backend reports the Virtual Library available at runtime: Windows, the `store` release channel (`app/release_channel.rs`) **and** real Package Identity (`app/package_identity.rs`, `GetCurrentPackageFullName`), combined by `is_available_at_runtime` in `virtual_library_root.rs`. The compile-time channel flag alone never enables it, so a Store-labelled unpackaged run (`tauri dev`, a binary started from `target`) hides the section. There is still no `lymic-shell-ext` shell extension and no `windows.cloudFiles` or COM server declaration in the MSIX manifest (the gate prototype's `Register` failed with 0x80070490 with one), and the Virtual Library is unavailable on macOS, Linux and the GitHub/NSIS channel. Even as designed in [ADR-0003](../adr/0003-windows-virtual-cloud-library.md), the **Virtual Library** is strictly read-only and separate from **Synchronization**: Explorer delete, move, and write operations are denied so uploads and asset lifecycle remain exclusively in **Watched Folders** and **Synchronization**. Preserve that boundary unless the product decision explicitly changes it.

Use the defined terms in [`GLOSSARY.md`](../../GLOSSARY.md): **Watched Folder**, **Removable Watched Folder**, **Target Album**, **Album Assignment**, **Upload Unit**, **Duplicate**, **Trashed Duplicate**, **Synchronization**, **Download**, **Virtual Library**, **Virtual Placeholder**, **Hydration**, **Explore Overview**, **Place**, **Place Timeline**, **Memory**, **Memory Timeline**, **Search**, **Search Mode**, **Search Filter**, **Search Results**, **Location**, **Tag**, **Tag Timeline**, **Restore**, **Move to Trash**, **Archive** and **Unarchive**. Target-album behaviour is governed by [ADR-0001](../adr/0001-folder-target-albums.md); removable-volume behaviour is governed by [ADR-0002](../adr/0002-removable-watched-folders.md); the planned read-only Windows Virtual Library design is recorded in [ADR-0003](../adr/0003-windows-virtual-cloud-library.md); Album Timelines and Place Timelines use paginated metadata search ([ADR-0006](../adr/0006-album-timeline-data-source.md), [ADR-0007](../adr/0007-place-timeline-metadata-search.md)); Search requires Immich 3.2 and has two result presentations ([ADR-0008](../adr/0008-search-requires-structured-filter.md), [ADR-0009](../adr/0009-search-results-two-presentations.md)); a Trashed Duplicate stays in the Immich trash and is reported ([ADR-0010](../adr/0010-trashed-duplicates-stay-in-the-trash.md)); Move to Trash is a soft delete on explicit user action only ([ADR-0011](../adr/0011-move-to-trash-is-a-soft-delete-on-explicit-user-action.md)); Archive and Unarchive change only the visibility between `timeline` and `archive` ([ADR-0012](../adr/0012-archive-and-unarchive-change-only-visibility.md)).

## Runtime shape

```text
Svelte 5 UI (src/)
  invoke commands / subscribe to events
        │
        ▼
Tauri command layer (src-tauri/src/commands/)
        │
        ▼
Rust application services
  sync/  watched_folders/  watcher/  immich/  db/  audit/  app/
        │              │        │
        ▼              ▼        ▼
 Immich REST API    local FS   SQLite + native keyring
```

`src-tauri/src/app/mod.rs` is the runtime composition root. It registers every Tauri command, starts background work, creates the tray, and hides (rather than quits) the main window on close.

## Synchronization lifecycle

1. **Discover:** startup, a manual sync, adding a folder, or watcher events produce a scan. Watcher overflow triggers a rescan.
2. **Classify:** the media layer forms an **Upload Unit** from one asset or an allowed live-photo pair and finds an optional XMP sidecar.
3. **Hash:** unchanged files reuse a cached checksum only when current size and mtime match. Others are streamed while hashing.
4. **Check:** checksum batches go to Immich's bulk-upload check; existing assets (Duplicates) are not uploaded. A Duplicate without an asset ID in the check result is looked up with `POST /api/search/metadata {"checksum", "withDeleted": true}`. A Trashed Duplicate (the check's `isTrashed: true`, or the search item's `isTrashed`) is left in the Immich trash, never uploaded again or restored, and reported as a `WARN` activity log entry `log_duplicate_in_trash` (`{file}`) plus the audit event `sync.duplicate.trashed` (ADR-0010). The activity log is the only place it is reported: the Dashboard shows only progress and the Failed Syncs panel, and a Trashed Duplicate is not a Failed Synchronization.
5. **Queue and process:** missing assets are durably enqueued, then streamed as multipart uploads with configured parallelism.
6. **Assign and record:** when a Watched Folder has a Target Album, both uploaded and duplicate remote assets are assigned to it, Trashed Duplicates included; if Immich refuses that assignment the normal Target Album failure path applies. Queue outcomes, remote IDs, failures, and progress are persisted.

The durable queue is the recovery boundary: `RUNNING`, `PAUSED`, `FAILED`, and `IDLE` live in `sync_jobs`; `PENDING`, `SYNCED`, and `FAILED` entries live in `sync_queue`. The Synchronization lifecycle coordinates job transitions and runner claims. On restart, pending work without a runner is recovered as paused; resume it from the queue rather than scanning folders again.

## Invariants to preserve

- Watched Folder paths are normalized; duplicates and parent/child overlaps are rejected.
- An unavailable folder remains configured and is retried by watcher reconciliation; it is not silently removed.
- Pause is durable and becomes effective at a safe queue boundary. Resume must be safe after restart.
- A Target Album is copied to the queue entry at enqueue time. Never fall back silently to the root library when its album operation fails.
- Persist `remote_id` after upload so an album-assignment retry does not re-upload the asset.
- Synchronization never restores, deletes or re-uploads a Trashed Asset, and never moves a Remote Asset into the trash. A Trashed Duplicate counts as synchronized and is reported, not failed (ADR-0010).
- Move to Trash and Restore are the only Immich writes that touch trash state, both need `asset.delete`, and both run only on explicit user action. Move to Trash always sends `force: false` (never `true`), never deletes permanently or empties the trash, never touches a local file, and is never offered in the Trash Timeline or the Virtual Library (ADR-0011).
- Synchronization never reads or writes an Archived Asset's visibility. Lymic writes visibility only on explicit user action through Archive and Unarchive, only the values `archive` and `timeline` (never `locked` or `hidden`), and never moves an asset into or out of the trash through them (ADR-0012). The server accepts the other values, so the restriction lives in `AssetVisibility` and the command.
- Credentials (API key and optional Cloudflare Access token) stay in the native keyring, never SQLite, logs, errors, or UI events.
- Server URLs are HTTPS by default. HTTP is allowed only after explicit opt-in for loopback hosts; credentials in URLs, redirects, query strings, and fragments are rejected.
- Upload and hashing I/O stream files; do not introduce full-file buffering.
- Keep Tauri command names and event names/payloads synchronized with their Svelte callers. `sync-event-subscription.ts` is the frontend event contract.

## Boundary contracts

The map controller (`src/lib/controllers/map-controller.svelte.ts`) owns the session marker snapshot; `MapView.svelte` renders it and opens the shared Lightbox. The registered `get_map_markers` command uses `GET /api/map/markers` through the domain-specific map desktop adapter.

### Tauri IPC

Commands are registered in `app/mod.rs`; implementations live in `commands/`. The command groups are `auth`, `albums`, `timeline`, `people`, `places`, `tags`, `memories`, `search` (`commands/search.rs`, `commands/search_suggestions.rs`), `folders`, `sync`, and `settings`. `get_filtered_timeline_buckets` (argument `timeline`) and `get_filtered_timeline_bucket_assets` (arguments `timeline` and `timeBucket`) are the two read-only commands of every Filtered Timeline; `timeline` is `"favorites"`, `"archive"` or `"trash"` (`FilteredTimeline` in `immich/timeline.rs`, `FilteredTimeline` and `FILTERED_TIMELINES` in `contracts.ts`), and any other value is rejected before a request is sent. The adapter is `FilteredTimelineDesktopAdapter` (`getFilteredTimelineBuckets`, `getFilteredTimelineBucketAssets`). Adding a Filtered Timeline means a `FilteredTimeline` variant with its filter constant in `immich/timeline.rs`, its name in `FILTERED_TIMELINES`, its `filteredTimelineViews` entry in `+page.svelte`, and its locale keys. `restore_trashed_assets` (argument `assetIds`, adapter `TrashRestoreDesktopAdapter`) is the one Immich write the Trash Timeline performs. `set_assets_visibility` (arguments `assetIds` and `visibility`, adapter `AssetVisibilityDesktopAdapter`, result `{ changedAssetIds }`) is the one write behind Archive and Unarchive; `visibility` is `"archive"` or `"timeline"` (`AssetVisibility` in `immich/archive.rs` and `contracts.ts`) and any other value is rejected at deserialization before a request is sent. `trash_assets` (argument `assetIds`, adapter `TrashMoveDesktopAdapter`, contract `TrashMoveResult { movedAssetIds, failureCode? }`) is Move to Trash, a soft delete that needs `asset.delete`: it rejects an empty list or an empty ID, and every requested asset not in `movedAssetIds` is still in the library (see [Move to Trash](#move-to-trash)). All of them are in `commands/timeline.rs` and routed through `ImmichSession::with_stored_credentials`. `get_asset_details` belongs to the timeline surface and supplies the Lightbox with a Remote Asset's original filename, favorite status, and optional EXIF details. `set_asset_favorite` changes a Remote Asset's favorite status. `download_asset` streams a Remote Asset's original file to the user-chosen Download path. `download_archive` retrieves Immich's ZIP archive, opens the native save dialog with Immich's safe suggested filename, and streams it to the selected path. `add_assets_to_album` adds one or more Remote Assets to an existing Album and reports successful and failed assignments. The Explore commands are read-only: `get_places` (`commands/places.rs`) lists Places; `get_place_timeline` (`commands/timeline.rs`, argument `city`) returns a Place's complete Timeline Buckets and assets; `get_memories` (`size`, clamped to 1-100) returns the newest Memories with their assets, and `get_memories_page` (`page`, 1-based, and `size`) returns a `MemoriesPage` for All Memories (both in `commands/memories.rs`). The People section reuses `get_people` and the `get_person_timeline_*` commands; there is no Explore-specific people command. The Tags commands are read-only and routed through `ImmichSession::with_stored_credentials`: `get_tags` (`commands/tags.rs`) lists every Tag as a flat list, and `get_tag_timeline_buckets` (argument `tagId`) and `get_tag_timeline_bucket_assets` (arguments `tagId` and `timeBucket`) in `commands/timeline.rs` supply a Tag Timeline (see [Tags](#tags)). `get_asset_details` also returns the optional `tags` of a Remote Asset for the Lightbox chips. The Search commands are all read-only and routed through `ImmichSession::with_stored_credentials`: `get_search_support`, `get_search_features`, `search_assets`, `search_context_page` (`page`) and `get_search_suggestions` (see [Search](#search)); the Recognized People filter reuses `get_people` and the city filter reuses `get_places`. Shared frontend IPC contracts live in `src/lib/contracts.ts`, and domain-specific adapter interfaces live in `src/lib/tauri/desktop-adapter.ts`. When changing a command, update its contract, domain adapter interface, owning caller (controller or component), and tests in the same change.

The backend emits `sync-progress`, `sync-progress-percent`, `sync-started`, `sync-transfer-stats`, `sync-progress-snapshot`, `sync-paused`, `sync-resumed`, `sync-error`, `log-message`, and `sync-idle`. Keep event names and serialized payloads backward-compatible within the application release.

### Immich

The core API calls are `GET /api/users/me`, `POST /api/assets/bulk-upload-check` (Lymic reads `assetId` and `isTrashed` of a duplicate), `POST /api/assets`, `POST /api/search/metadata` with `checksum` and `withDeleted: true` (Duplicate lookup, including Trashed Assets; `immich/album.rs`), `GET /api/timeline/buckets`, `GET /api/timeline/bucket` (the Photo Timeline and the Favorites Timeline call both with `visibility=timeline`, so Archived Assets are left out as in Immich Web; the Archive Timeline calls both with `visibility=archive`, see [Archive Timeline](#archive-timeline); the Trash Timeline calls both with `isTrashed=true`, see [Trash Timeline](#trash-timeline)), `GET /api/assets/{id}`, `PUT /api/assets/{id}` (favorite status), `PUT /api/assets` (bulk and per-asset fallback visibility update of Archive and Unarchive, `asset.update`, see [Archive Timeline](#archive-timeline)), `POST /api/trash/restore/assets` (Restore, see [Trash Timeline](#trash-timeline)), `DELETE /api/assets` with `{"ids":[...],"force":false}` (Move to Trash, see [Move to Trash](#move-to-trash)), `GET /api/search/cities` (Places, one Remote Asset per city, `asset.read`; `immich/places.rs`), `POST /api/search/metadata` with `city`, `withExif`, `order=desc`, `page` and `size=1000` (Place Timeline, `asset.read`, ADR-0007), `GET /api/memories?size=N&order=desc` (Memories, `memory.read`; `immich/memory.rs`), `GET /api/tags` (Tags, `tag.read`; `immich/tags.rs`), `GET /api/timeline/buckets` and `GET /api/timeline/bucket` with `size=MONTH` and `tagId` (Tag Timeline, `asset.read`), the optional `tags` of `GET /api/assets/{id}` (Lightbox chips; see [Tags](#tags)), `GET /api/server/version`, `GET /api/server/features`, `POST /api/search/metadata`, `POST /api/search/smart` and `GET /api/search/suggestions` (Search, `asset.read`; see [Search](#search)), `GET /api/assets/{id}/thumbnail`, `GET /api/assets/{id}/original`, `POST /api/download/archive` (ZIP downloads), and `PUT /api/albums/{id}/assets` (album assignment); album behaviour is in `immich/album.rs` and timeline behaviour is in `immich/timeline.rs`. `GET /api/memories` has no offset or page parameter, so `get_memories_page` requests `size = page * pageSize + 1` Memories, drops the earlier pages, and treats the one extra Memory as the sign that a next page exists; paging counts Memories as Immich returns them, before Memories without dated assets (which cannot be shown) are dropped; a Memory's cover is the first asset that appears in its timeline. Memory responses embed their assets with EXIF and are read with a 32 MiB response cap instead of the default cap. Do not use `/api/search/explore`. Requests use `x-api-key`; bulk checks and uploads use the SHA-1/Base64 checksum contract. Changes to endpoints or payloads require checking the supported Immich API contract rather than guessing.

#### Back, `tagOrigin` and scroll positions

`+page.svelte` holds one `tagOrigin` (a `ViewPosition` `{ view, top }` from `view-position.ts`, the same type as `searchOrigin` and the argument of `returnTo`; `tag-origin.ts` holds the default and `recordTagOrigin`): the view a Tag Timeline was opened from and its scroll position. `selectTag` records it with `recordTagOrigin`, which overwrites it only when the Tag Timeline is opened from a view other than a Tag Timeline, so Back after hopping from chip to chip returns to where the chain started, not to the previous Tag. It defaults to the Tags view at the top. The origin can be any view, including the sub-views (an Album, Person, Place or Memory Timeline), the Map and the Search Results. Back (`tags_timeline_return`, "Back to {view}") returns there through the shared `returnTo`, which restores the origin's scroll position (timeline views through `scrollRestore`, other views through the content scroll position) and reloads the Tags view if it went stale. A Tag Timeline opened from another Tag Timeline is a new controller (`{#key tagTimeline}`), so it starts at its top. The Tags view keeps its own scroll position (`tagsScrollTop`) like Explore and People. Sign-out resets `tagOrigin`, `tagsScrollTop`, the open Tag Timeline and the Tags controller (tree, expansion choices, stale flag) through `session-controller.svelte.ts` and `resetView`.

#### Refresh

The Tags controller reuses `createExploreListController` (generation guard, offline fallback, classified error, prefix `tags`) and `createRefreshWhenActive` (`refresh-when-active.ts`, shared with the Explore Overview). The tree reloads every time the view is opened. When a Synchronization settles while the Tags view is the open view it reloads at once (`refreshIfActive`, called from `onSyncSettled` in `session-controller.svelte.ts` with `isTagsActive`); when it settles while another view is open the tree is only marked stale and reloads once on return (`refreshIfStale`, called from `returnTo` when the origin is the Tags view); a Move to Trash from a Tag Timeline marks it stale the same way (#256). Tags that are already loaded stay visible when a reload fails because the network or server is unavailable (offline notice); a first load that fails shows the error with Retry.

#### Immich requests and errors

- `GET /api/tags` (`immich/tags.rs`, `tag.read`, no pagination): a flat array of `{ id, name, value, parentId?, color? }`. `value` is the full path. An absent, empty or whitespace-only `value` falls back to `name`, and an empty or whitespace-only `parentId` or `color` counts as absent; unknown fields are ignored. An entry without `id` or `name`, an unreadable body, or a body that is too large or cannot be read to the end, is `tags_invalid_response`. The `tags` of asset details are parsed leniently in the same file (`asset_tags_from_value`): an entry without a usable `id`, or with neither `name` nor `value`, is dropped, so one bad entry never fails the details request.
- `GET /api/timeline/buckets?size=MONTH&tagId=<id>` and `GET /api/timeline/bucket?size=MONTH&timeBucket=<bucket>&tagId=<id>` (`immich/timeline.rs`, `asset.read`), as for `personId`. The timelines and the Tags view do not use `tagIds`; the flat metadata search `tagIds` filter is deprecated since Immich v3.2.0 and is not used. Only the Search's Tag filter sends the structured `filter.tagIds` (see [Search](#search)).
- `GET /api/assets/{id}` may include a `tags` array (`immich/client.rs`), read leniently. A missing, null or non-array `tags` means "no Tags" (`None`), never an error. An entry without an `id`, or with neither `name` nor `value`, is dropped; a missing name falls back to the last segment of the path and a missing path to the name; one malformed entry never fails the request.

Failure codes are credential-free and never carry the response body: `tags_authentication_required` (401), `tags_permission_denied:tag.read` (403), `tags_unavailable` (transport failure and any other status) and `tags_invalid_response` (unparseable or wrongly shaped body, and a body that exceeds the response cap or fails while being read), produced by the shared `request_failure_code("tags", status, "tag.read")`. The shared classifier turns them into the permission-denied state, which names `tag.read`, the unavailable state (authentication required and unavailable alike) or a generic error. A Tag Timeline failure is the shared timeline load error and names no permission. Locale keys are `tags_*` and, for the chips, `timeline_info_tags` and `timeline_tag_open`, in every supported language.

#### Permissions

`tag.read` (Tags view), `asset.read` (Tag Timeline) and `asset.view` (thumbnails and Lightbox, as everywhere). A key without `tag.read` disables only the Tags view and the Search's Tag filter (each names the permission and offers Retry); Photos, Explore, Search and every other view keep working. The Lightbox chips need no `tag.read`: they come from the asset details the Lightbox loads anyway.

#### Not verified against a live Immich server

- **Parent Tag descendants.** Whether a parent Tag's timeline includes the assets of its child Tags is not verified; Immich's OpenAPI spec says only "Filter assets with a specific tag". Lymic has no descendant logic of its own: a Tag Timeline shows whatever Immich returns for that Tag, so a parent without assets of its own may show the empty state.
- **Minimum Immich version.** The Immich release that introduced `tagId` on the timeline endpoints and `tags` on asset details is not known. The OpenAPI spec (version `3.4.0-rc.0`) reflects only the current state, and no minimum version is documented. An older server was not tested; absent `tags` simply shows no chips.
- The shapes of `GET /api/tags` and of the `tags` in asset details come from the OpenAPI spec and Lymic's fake-server tests. The 2026-11-17 check against Immich v3.4.1 (see [Search](#search)) called `GET tags` on a library without Tags, so no Tag was observed, and how a key without `tag.read` is answered (assumed 403) was not tried.

### Archive Timeline

The Archive Timeline shows the authenticated user's Archived Assets in the shared `TimelineView` (Timeline Scrubber, Lightbox, Thumbnail Cache). Browsing it is read-only. Lymic can Unarchive its Remote Assets from the Lightbox and from a multi-selection, and Archive them from the Lightbox and the multi-selection of the Photo Timeline, the Favorites Timeline and the views that show archived and other assets together (Album, Person, Place, Memory and Tag Timelines, Search Results; [ADR-0012](../adr/0012-archive-and-unarchive-change-only-visibility.md)); the Lightbox and selection also offer Favorite, Download and Add to Album from `remote-asset-actions.svelte.ts`. A view offers one archive action, in its Lightbox and in its multi-selection alike: Archive in the Photo and Favorites Timelines, Unarchive here, and none in the Trash Timeline or the Map View. The mixed views listed above are the exception: their multi-selection offers Archive only, while their Lightbox offers Archive or Unarchive (or neither) depending on the open asset's `visibility` from its details. It is separate from Synchronization, Watched Folders and the Virtual Library, and persists nothing.

Immich calls (both need only `asset.read`; thumbnails and the Lightbox continue to need `asset.view`):

- `GET /api/timeline/buckets?size=MONTH&visibility=archive`
- `GET /api/timeline/bucket?size=MONTH&timeBucket=<bucket>&visibility=archive`

The requests carry no `isFavorite`, `isArchived`, `isTrashed` or `withPartners` parameter; the deprecated archived flag and metadata search are not used. Unlike the Favorites Timeline, a bucket's assets are not defaulted to favorites: `isFavorite` comes from the response. Buckets are sorted newest first. Failures are credential-free strings (`Failed to fetch archive timeline buckets: <status>`, `Failed to fetch archive timeline bucket: <status>`, `Invalid ... response`) and show the shared timeline load error. The one exception is HTTP 403: it returns the credential-free code `archive_permission_denied:asset.read` (the shared `request_failure_code` format, applied only to the Archive requests), which the Archive Timeline's controller classifies with `classifyRequestFailure(…, "archive")` and exposes as `permissionDenied`, so the view shows `archive_permission_error` (naming the missing `asset.read` permission) instead of `archive_error`, with Retry still available. ### Trash Timeline

The Trash Timeline shows the authenticated user's Trashed Assets in the shared `TimelineView` (Timeline Scrubber, Lightbox, Thumbnail Cache). Lymic performs exactly two writes that touch trash state: Restore and Move to Trash ([ADR-0011](../adr/0011-move-to-trash-is-a-soft-delete-on-explicit-user-action.md)). The Trash Timeline itself performs only Restore. Lymic never deletes a Remote Asset permanently, never empties the trash, and offers no "restore all". The Lightbox and multi-selection offer only Restore and Download (`allowFavoriteAndAlbum={false}` hides Favorite and Add to Album). It is separate from Synchronization, Watched Folders and the Virtual Library: viewing or restoring touches no local file, Watched Folder or Synchronization state, and nothing is persisted.

Immich calls as Lymic sends them (browsing needs `asset.read`; thumbnails and the Lightbox continue to need `asset.view`; Restore needs `asset.delete`, observed on v3.4.1):

- `GET /api/timeline/buckets?size=MONTH&isTrashed=true`
- `GET /api/timeline/bucket?size=MONTH&timeBucket=<bucket>&isTrashed=true`
- `POST /api/trash/restore/assets` with `{"ids":["<id>", ...]}`, reading `{"count": n}`: once for the whole selection and, only when that does not settle it, once per asset (see below)

The browse requests carry no `isFavorite`, `visibility`, `isArchived` or `withPartners` parameter. Buckets are sorted newest first, and `isFavorite` comes from the response. Failures of the browse calls are credential-free strings (`Failed to fetch trash timeline buckets: <status>`, `Failed to fetch trash timeline bucket: <status>`, `Invalid ... response`) and show the shared timeline load error. No minimum Immich version is gated, so a server that rejects the filter surfaces as that load error.

Restore validates the IDs (unique and path-safe) and first sends all selected IDs in one request. Observed on Immich v3.4.1 (see below), `count` is the number of requested IDs that exist and are accessible, not the number actually restored (IDs that were already restored count too), and one unknown or unowned ID makes Immich reject the whole request with HTTP 400 and restore nothing, not even the valid IDs. There is no per-asset result. Lymic therefore trusts the batch only when it answers 200 with a `count` equal to the number requested, in which case every asset is out of the trash. If the batch answers 400, or answers 200 with any other `count`, Lymic falls back to one request per asset: 200 with `count` 1 means that asset was restored, and 400 (or any other `count`) means it failed. A single selected asset is never requested twice. A stale ID, for instance one Immich removed permanently after its retention period while the view was open, can thus no longer block the others, and the partial-failure path (`trash_restore_partial`, failed assets staying selected, retry) occurs for real. Individual requests are sequential and idempotent. A 401, 403, 5xx, a transport error or an unreadable body in either phase aborts the whole call with a credential-free code and no partial result, so assets already restored by then stay in the view until it reloads; retrying is safe. The frontend treats every requested asset not named in `restoredAssetIds` as failed. Request-level failures never forward the response body: `trash_restore_authentication_required` (401), `trash_restore_permission_denied:asset.delete` (403, classified by `classifyRequestFailure(…, "trash_restore")`) and `trash_restore_unavailable` (any other status or a transport error). Lymic no longer reads `GET /api/assets/{id}` after a Restore.

### Move to Trash

Move to Trash puts Remote Assets into the Immich trash from the Lightbox and the timeline multi-selection of every view except the Trash Timeline, after an explicit confirmation ([ADR-0011](../adr/0011-move-to-trash-is-a-soft-delete-on-explicit-user-action.md)). Frontend: `trash_assets` (`TrashMoveDesktopAdapter.trashAssets`) is wired through the `trashAssets` prop of `TimelineView` (and `MapView`). The Lightbox shows a `Trash2` button next to Download (no keyboard shortcut), disabled while a Download, Album assignment, Restore, Archive or Unarchive, or another Move to Trash runs (the Archive and Unarchive button is disabled while a Move to Trash runs, for the same `isBusy`). It opens `MoveToTrashDialog.svelte` for every Move to Trash: it names the count (`trash_move_confirm_message`) and says the asset can be restored in the Trash; Cancel and Escape do nothing. `createRemoteAssetTrash` (`remote-asset-trash.ts`) makes one `trashAssets` request, removes the moved assets from the timeline at once and keeps every asset Immich did not confirm; it never rejects and classifies a refusal, whether it rejected the request or came back as the result's `failureCode`, with `classifyRequestFailure(…, "trash_move")`. On success the Lightbox closes and the view shows `trash_move_success`; a refusal shows `trash_move_permission` (it names `asset.delete`), any other failure `trash_move_failed`, in the Lightbox, which stays open with the asset in place. Marking the cached views stale (ADR-0011, Consequences) is described under "Cached views after a Move to Trash" below. If the timeline was refreshed or replaced while the request ran, the moved asset still leaves the timeline and the Lightbox still closes as long as it shows that asset: it never stays open on an asset Immich confirmed as moved (only the page-level feedback is dropped with the stale result).

Hosting views: `+page.svelte` puts its `trashAssets` wrapper around `desktop.trashAssets` into `sharedTimelineProps`, so every `TimelineView` it renders offers Move to Trash in the Lightbox and the multi-selection through the same owner modules, with no per-view code path: the Photo Timeline, the Favorites and Archive Timelines, the Album, Person, Place, Memory and Tag Timelines, and Search Results (`SearchResultsView` forwards `sharedTimelineProps`, in both presentations). The Trash Timeline is the only opt-out: its `filteredTimelineViews` options set `trashAssets: undefined` and keep Restore and Download. Move to Trash coexists with Archive and Unarchive ([Archive Timeline](#archive-timeline), ADR-0012) in the views that offer both, with its own button (`Trash2`) beside the archive button in the Lightbox and the selection toolbar, and its own confirmation dialog, which Archive and Unarchive do not have; the Trash Timeline offers neither Archive nor Unarchive, and the Archive Timeline offers Unarchive and Move to Trash. The Map View is not a `TimelineView`: `MapView.svelte` takes the same `trashAssets` prop and gives its Lightbox `onTrash`, which runs `createRemoteAssetTrash` against the marker snapshot (`MapViewState.removeMarker`); on success the marker is removed, the Lightbox closes, the view shows `trash_move_success` and an open location results list is closed so the map rebuilds without the asset. Map View has no multi-selection. Assets the user does not own (for example in a shared Album) are not filtered out beforehand: Immich answers 400 for them, they follow the partial-failure path and stay visible and selected. The cached views that may still show a moved asset are marked stale by the same wrapper (#256, below).

#### Cached views after a Move to Trash

Every Move to Trash (Lightbox, multi-selection, Map View) goes through one `trashAssets` wrapper in `+page.svelte`, which is also what `sharedTimelineProps` and `MapView` receive. After a request that moved at least one asset (`movedAssetIds` not empty, also when the result carries a `failureCode` because the request stopped midway; a refusal, a failure or a request that moved nothing changes nothing) it marks the cached views stale so they reload on their next open, and only then:

| View | What the wrapper does | Reloads |
| --- | --- | --- |
| Photo Timeline | `navigation.markPhotosStale()` unless the view the move started in was the Photo Timeline (it already dropped the asset with `removeAsset`). Shares the flag of Restore. | Once, when Photos next opens (`openPhotos`) or is returned to from a Search or Tag Timeline started in it (`returnTo` calls `navigation.refreshPhotosIfStale()`). |
| Explore Overview | `explore.refreshIfActive()`: the Explore Overview is never the view a move runs in, so this only marks it stale; it reloads People, Places and Memories together. | Once, on return from a Person, Place or Memory Timeline (`returnToExplore`, `returnTo` call `refreshIfStale`). Opening it from the navigation always reloads it anyway. |
| Tags | `tags.refreshIfActive()`, which likewise only marks the tree stale. | Once, on Back from a Tag Timeline (`returnTo` calls `refreshIfStale`). Opening it from the navigation always reloads it anyway. |
| Albums catalogue | `navigation.markAlbumsStale()`, whatever view the move ran in (it can also run in a Search started in an Album Timeline). | Once, on Back from an Album Timeline (`returnToAlbums` calls `refresh.albums()` when the flag is set). Opening Albums from another view (`openAlbums`) always reloads it and clears the flag, so a move elsewhere never causes a second reload; nothing reloads when no asset was moved. Same mechanism as `markPhotosStale` and `refreshPhotosIfStale`; `reset` clears it. |

No request is made for the view the move ran in, and moving inside the Photo Timeline does not mark Photos stale. Favorites, Archive and Trash reload every time they open; Album, Person, Place, Memory and Tag Timelines are created or refreshed every time they open.

Checked, no further flag added:

- **Albums catalogue**: `navigation.openAlbums` calls `albumCatalogue.refresh()` every time the Albums entry is opened from another view, so it re-reads Immich, which stops counting a trashed Album member (verified in #253). Back from an Album Timeline (`returnToAlbums`) restores the cached catalogue, so it has its own stale flag (table above) and re-reads only when an asset was moved since.
- **Map marker snapshot**: `navigation.openMap` calls `map.refresh()` every time the Map entry is opened, and a move inside the Map View already removes the marker (`removeMarker`), so a trashed asset does not return as a marker.

Tests are page-level (`+page.svelte.test.ts`, "Cached views after a Move to Trash"); the Map View is not covered there because it needs a real map.

Multi-selection: the selection bar of every timeline that offers Move to Trash shows a `Trash2` Move to Trash button (label `trash_move`) when `trashAssets` is set. It opens the same `MoveToTrashDialog` naming the selected count; Cancel, Escape and the backdrop do nothing. Confirming runs `trash` of `timeline-selection-actions.svelte.ts` (`SelectionAction` is now `favorite | album | download | restore | trash`), modelled on Restore: one `trashAssets` request for the selection through `createRemoteAssetTrash`, a second bulk action (or a second Move to Trash) is ignored while `busyAction` is set, the button and the others are disabled and the dialog's buttons are disabled with a spinner. Moved assets leave the timeline at once (`removeAsset`, then `selection.forget`), the selection shrinks to the assets Immich did not confirm so the user can retry, and a result that arrives after `reset` (timeline refreshed or replaced, logout) is dropped with no feedback and no busy state left. The dialog closes whatever the outcome; the result is shown as `selection.trashFeedback`, which the Lightbox flow shares (`trashOne`, the multi-selection's single-asset twin of `restoreOne`). `trashFeedbackFor(outcome, total)` decides it: all moved is `trash_move_success` (count); some failed is `trash_move_partial` (names how many of the total failed, says they stay selected); none moved is `trash_move_none` (names how many failed); a refusal is `trash_move_permission`; any other failed request is `trash_move_failed`. A single asset that was not moved is `trash_move_failed`, not "1 of 1", in the Lightbox. Backend: nothing new for the multi-selection; the batch-then-per-asset fallback serves both (a batch of N is one `DELETE`, a 400 turns it into N single-asset `DELETE`s, a single asset is never requested twice, 401, 403, any other status including a non-204 success, and a transport error abort). Chunking very large selections is not done (Immich's batch limit is unverified, see the verification below).

Partial result of an aborted fallback: `trash_assets` resolves with `{ movedAssetIds, failureCode? }` (Rust `TrashMoveResult`, TypeScript `TrashMoveResult` in `contracts.ts`; `failureCode` is left out of the serialized result when absent). If a 401, 403, 5xx, non-204 success or transport error ends the per-asset fallback after at least one asset was moved, the result lists those assets and carries the credential-free code (`trash_move_authentication_required`, `trash_move_permission_denied:asset.delete` or `trash_move_unavailable`); the assets after the abort were not attempted. `createRemoteAssetTrash` removes the moved assets from the view, keeps the others visible (and selected in a multi-selection) and maps the code to `outcome.failure` (`permission` or `error`), so `trashFeedbackFor` shows `trash_move_permission` or `trash_move_failed` rather than a count message; the `trashAssets` wrapper in `+page.svelte` marks the cached views stale because `movedAssetIds` is not empty. A failure before any asset was moved is unchanged: the command rejects with the code alone (the batch request itself aborted, or the first individual request that was not refused with 400 aborted, so only 400s precede it), every requested asset stays visible and no cached view is marked stale. Retrying after either is safe because Move to Trash is idempotent. The Lightbox and the Map View send one asset, which has no fallback, so they never see a partial result. This replaces the earlier "abort with no partial result" rule.

What this relies on, observed live on v3.4.1 (see the verification below, one server version only): a per-asset `204` means that asset is in the trash and a per-asset `400` means it was not changed, so the moved list is exact; an asset that is already trashed answers `204`, so a retry is harmless; and a key without `asset.delete` answers `403` before any ID is looked at. The abort in the middle of the fallback itself (a key revoked, or the server going down or answering 5xx between two requests) was not provoked live; it is covered by the fake-server tests in `immich/trash.rs` (credential, 5xx, non-204 success and transport aborts after a moved asset, and the same aborts before any moved asset), by `remote-asset-trash.test.ts` and by the page-level tests.

Immich call as Lymic sends it (needs `asset.delete`, observed on v3.4.1): `DELETE /api/assets` with `{"ids":["<id>", ...],"force":false}`. `force` is never `true`; `never_sends_force_true_in_any_request_body` in `immich/trash.rs` covers that. IDs are validated (unique, path-safe, non-empty list) like Restore before any request.

Batch behaviour the implementation follows (from the verification below):

- The batch is all-or-nothing and has no per-asset result and no count. `204 No Content` with an empty body means every requested asset is now in the trash (assets that were already trashed are harmless). Lymic trusts the batch only on 204.
- A `400` for the batch means at least one ID is unknown, not owned, in the locked folder or malformed, and Immich changed nothing, valid IDs included. Lymic then falls back to one request per asset, as Restore does: `204` means that asset was moved, `400` means it was not moved and the next asset is tried. A single selected asset is never requested twice.
- `401`, `403`, any other status and a transport error abort the call with a credential-free code in either phase (an error when nothing was moved yet, `failureCode` next to the moved IDs when the fallback had already moved some, see "Partial result" above): `trash_move_authentication_required`, `trash_move_permission_denied:asset.delete` and `trash_move_unavailable` (classifier prefix `trash_move`). The body is never forwarded. The frontend treats every requested asset that is not in the returned `movedAssetIds` as still in the library.
- Unlike Restore there is no `count` to compare, so the only trigger for the per-asset fallback is a `400`.
- The fake server must answer: `204` with an empty body (batch or single asset, all IDs accessible); `400 {"message":"Not found or no asset.delete access"}` when any ID is unknown or not owned (nothing changed); `403 {"message":"Missing required permission: asset.delete"}` for a key without the permission (checked before any ID is looked at); `401 {"message":"Authentication required"}` or `401 {"message":"Invalid API key"}`; and `400 {"message":"Validation failed","errors":[...]}` for a malformed ID.

#### Verification of the Move to Trash write (#253)

Verified live on 2026-11-20 against Immich **v3.4.1** (`ghcr.io/immich-app/immich-server:v3` from the official Docker compose, ML service not started). The instance was a scratch compose project holding only test assets: an admin with seven assets from earlier checks, roughly 150 generated JPEGs added for this check, and a second user created for it with two assets. The check was scripted HTTP calls with API keys of different permissions (all permissions; `asset.read`, `asset.view`, `asset.update`, `asset.upload` and `album.read` without `asset.delete`; `asset.delete` only; `asset.delete` plus `asset.read`; and an all-permissions key of the second user), not a run through the Lymic UI. It covers **one server version only**; Lymic claims no minimum Immich version. `force: true` was never sent. Anything not observed stays listed as unverified.

| Assumption | Status | Observed outcome |
| --- | --- | --- |
| `DELETE /api/assets` with `{"ids":[...],"force":false}` moves assets to the trash and answers with no body. | CONFIRMED (v3.4.1) | `204 No Content` with an empty body, for one ID, for three and for 120 valid IDs. `GET /api/assets/{id}` then reports `isTrashed: true` (the details carry no trash timestamp). A video was not tried (unverified). |
| A batch with one unknown or unowned ID fails as a whole with 400 and trashes nothing, valid IDs included. | CONFIRMED (v3.4.1) | `[valid, unknown UUID]`, `[unknown, valid]` and `[own, other user's asset]` all answered `400 {"message":"Not found or no asset.delete access"}`; the valid asset stayed `isTrashed: false`. An unknown ID alone is the same 400. There is no per-asset result, so the batch-then-per-asset fallback is needed, as for Restore, but it is triggered only by a 400 (there is no count). |
| An asset owned by another user cannot be trashed, whoever asks. | CONFIRMED (v3.4.1) | The other user's asset alone: `400 "Not found or no asset.delete access"`, unchanged, also with the admin's all-permissions key. An asset in an Album shared with the key's user as editor is the same 400, both ways round (the admin on the second user's shared Album, the second user on the admin's), alone and inside a batch with an own asset. This is the partial-failure path of the spec, not an error of the whole action. Partner-shared assets were not tried (unverified). |
| An asset that is already in the trash is harmless (idempotent). | CONFIRMED (v3.4.1) | Alone and in `[already trashed, live]`: `204`, and the live asset was trashed too. The per-asset fallback therefore counts a `204` for an already-trashed asset as moved. |
| An empty `ids` list is harmless. | CONFIRMED (v3.4.1) | `204`, nothing changed. Lymic rejects an empty list before any request anyway. |
| A duplicate ID in one batch is harmless. | CONFIRMED (v3.4.1) | `[id, id]` answered `204` and trashed the asset. |

Without any key: `401 {"message":"Authentication required"}`; with a bogus key: `401 {"message":"Invalid API key"}`. A key that can Restore therefore needs no new permission. |

Lymic nevertheless always sends `force: false` explicitly. `force: true` (permanent deletion) was deliberately never sent, so its behaviour is unverified here. |
| A Favorite or an Archived Asset can be trashed and keeps its flags. | CONFIRMED (v3.4.1) | One batch `[favorite, archived, plain]` answered `204`. Afterwards the details reported `isFavorite: true` for the favorite and `visibility: "archive"` for the archived asset, both with `isTrashed: true`. |

The timelines Lymic already shows are consistent after a reload, and the assets are findable in the Trash Timeline. |
| A hidden asset (visibility `hidden`, such as a Live Photo's video) can be trashed. | CONFIRMED (v3.4.1) | `204`; the details reported `visibility: "hidden"` and `isTrashed: true`. Trashing a Live Photo's still image and what happens to its hidden video was not tried (unverified). |
| An asset in the locked folder cannot be trashed. | CONFIRMED (v3.4.1): not reachable | A locked asset is treated as not found: alone `400 "Not found or no asset.delete access"`, and in `[live, locked]` the same 400 with the live asset untouched. Its details answer `400 "Not found or no asset.read access"`. A batch containing one falls back to per-asset requests. An elevated (PIN) session was not tried; Lymic never has one. |
| An Album and Album searches stop counting a trashed member. | CONFIRMED (v3.4.1) | After trashing one of two members of an own Album, `GET /api/albums/{id}` and `GET /api/albums` reported `assetCount: 1` and no longer listed it; `POST /api/search/metadata` with `albumIds` returned one asset, and two with `withDeleted: true`. So the Album, Person, Place, Memory and Tag timelines no longer show it after their next load, and the Albums catalogue count is right after a reload. The Map marker snapshot was not checked: the test assets carry no GPS position (unverified). |
| Uploading the same file again reports a duplicate and leaves the asset in the trash. | CONFIRMED (v3.4.1) | Uploading the bytes of a just-trashed asset again answered `200 {"status":"duplicate","id":<the same ID>}`, and the asset stayed `isTrashed: true`. This is the Trashed Duplicate path of [ADR-0010](../adr/0010-trashed-duplicates-stay-in-the-trash.md). A Lymic Synchronization run itself was not executed (unverified). |
| Restore brings a moved asset back. | CONFIRMED (v3.4.1) | `POST /api/trash/restore/assets` answered `200 {"count":1}` and the details reported `isTrashed: false`; the asset could be trashed again (`204`). A Restore of `[trashed, live]` answered `{"count":2}`, the already known "count is the number of requested IDs that exist" behaviour. |

Not observed and still unverified: a video asset, a Live Photo and its hidden video partner, stacked assets, partner-shared assets, a batch larger than 120 IDs (Immich's limit, if any, is unknown, so very large selections may need chunking), the Map marker snapshot, the retention period and what Immich does when it expires, permanent deletion (`force: true`, deliberately not sent), behaviour on other Immich releases, a Lymic Synchronization run over a trashed asset, and the Lymic UI flow against the live server. To re-run the check against another server or release, send `DELETE <server>/api/assets` with header `x-api-key: <key>` and body `{"ids":["<id>"],"force":false}` for each case above against a throwaway library, record status and body, and read `GET /api/assets/{id}` afterwards. Never use real data.

### Search

Search is a read-only query over the whole Immich Library from a search bar at the top of every view, with a text, one Search Mode and any number of Search Filters ([ADR-0008](../adr/0008-search-requires-structured-filter.md), [ADR-0009](../adr/0009-search-results-two-presentations.md)). It never changes a Remote Asset, is separate from Synchronization, Watched Folders and the Virtual Library, and persists nothing. It requires Immich 3.2 or later; every other view keeps its own requests and works on older servers. The Tag filter chooses Tags from the hierarchy of the Tags view (see [Tags](#tags)) and needs `tag.read`; a key without it disables only that filter.

#### Immich requests

All Search requests use `x-api-key` and need `asset.read`. The structured `filter` is the only filter mechanism: no flat field (`personIds`, `city`, `takenAfter`, `rating`, `isNotInAlbum`, `page`, `order`) is ever sent, because Immich rejects a request that mixes them with `filter`.

- `GET /api/server/version` (64 KiB cap): `{major, minor, patch, ...}`. The Search is supported when `(major, minor) >= (3, 2)`. Only a "supported" answer is remembered; an unsupported one is asked again with the next Search. Held in memory.
- `GET /api/server/features`: `smartSearch` and `ocr`; a flag the server does not report counts as off. Read once before the first Search and held in memory; a failure leaves the features unknown (everything stays available) and is read again with the next Search.
- `POST /api/search/metadata` (every chronological Search, also a Context Search without text): `{ filter, orderBy: { field: "localDateTime", direction: "desc" }, size: 1000, withExif: true, cursor? }`. Pages follow `assets.nextCursor` until it is empty or 5 000 results are held (`SEARCH_RESULT_LIMIT`); a repeated cursor or an empty page that promises another page is `search_invalid_response`; a failed page fails the whole load. Results are grouped into Timeline Buckets in local time; assets without a usable capture time are omitted. Responses are read with a 32 MiB cap.
- `POST /api/search/smart` (a Context Search with text): `{ query, filter, size: n * 100, withExif: true }` with no `page`. Immich's structured smart search has **no paging**: it rejects `page` next to `filter` and answers without a next page. Page `n` of the relevance presentation therefore asks for the best `n * 100` results (at most 1 000, `CONTEXT_RESULT_LIMIT`, Immich's maximum `size`), keeps the last 100 and offers page `n + 1` only while the answer filled the window. A Context Search shows at most the best 1 000 results: the page that fills the 1 000 window carries `limitReached`, which the controller reports as `truncated` and the results view shows as a notice (`search_context_limit`).
- `GET /api/search/suggestions?type=<country|state|camera-make|camera-model|camera-lens-model>` with optional `make` (models), `country` and `state` narrowing; blank and null suggestions are dropped. Needs `asset.read`. Cities have no suggestion type here: the city filter uses the Explore city listing (`GET /api/search/cities` through `get_places`, names kept exactly as returned).
- The Recognized People filter lists people through `get_people` (`person.read`; named people first, unnamed ones also selectable).
- The Tag filter lists Tags through `get_tags` (`tag.read`) from the same Tags controller as the Tags view (`SearchFilterTag.svelte`, which shows the Tag tree through the shared `TagTree.svelte` in multi-select mode: `aria-multiselectable`, a check mark on chosen Tags, the arrow keys, Enter and Space as in the Tags view). The Tags are read once when the panel is opened and only if the Tags view has not loaded them. The chosen Tags stay in the filter whatever the load does, and the filter shows how many are chosen with a control to clear them (`search_filter_tag_chosen`, `search_filter_tag_clear`), also when the Tags cannot be loaded (for example without `tag.read`) and the tree is hidden. While the Tags are offline the loaded tree stays visible with the `tags_offline` notice and the choice is left alone. After a successful load that is not the offline cache, a chosen Tag that Immich no longer returns is dropped from `tagIds`, so the Search does not silently match nothing; `tagIds` is cleared when none is left. That an unknown Tag id matches nothing was observed only for `personIds`; for `tagIds` it is not verified (see the live check). This `tagIds` is the **structured search filter** field: it is neither the deprecated flat `tagIds` of the metadata search (never sent) nor the timeline's `tagId` (one Tag, used by the Tag Timeline).

| Search input | Key and condition |
| --- | --- |
| Text, Filename | `originalFileName: { like: "%text%" }` |
| Text, Description | `description: { like: "%text%" }` |
| Text, Folder Path | `originalPath: { like: "%text%" }` |

| Date | `takenAt: { gte, lte }`, either optional; start of the first and end of the last local day as UTC instants |
| Media type | `type: { eq: "IMAGE" }` or `{ eq: "VIDEO" }` |
| Recognized Persons | `personIds: { all: [ids] }` (omitted when none) |
| Tags | `tagIds: { all: [ids] }` (omitted when none); exactly the chosen Tags, their children are not added. `all` is NOT VERIFIED on a live server. |
| Favorite | `isFavorite: { eq: true }` |
| Archived option | `visibility: { eq: "archive" }`; **always sent**, as `{ eq: "timeline" }` when the option is off |
| Unfiled | `hasAlbums: { eq: false }` |
| Rating | `rating: { eq: n }`, n from 1 to 5 |
| Camera | `make`, `model`, `lensModel`: `{ eq: value }` with the suggestion exactly as Immich returned it |
| Location | `country`, `state`, `city`: `{ eq: value }`; country and state from suggestions, city from the city listing |
| Always | `trashedAt: { eq: null }`: Trashed Assets are left out (see below) |

The text is trimmed; `%`, `_` and `\` are escaped with a backslash. Immich's `like` already means "contains" (it wraps the value in `%...%` itself), so Lymic's own `%` wrapping is redundant but harmless. A Search with neither text nor any set Search Filter does not run (`canSubmit`).

#### Errors

Credential-free codes, never the response body: `search_authentication_required` (401), `search_permission_denied:asset.read` (403), `search_unavailable` (transport failure and any other status, including a 500 when Immich's machine-learning service is unreachable), `search_invalid_response` (unreadable body, repeated cursor), `search_invalid_request` (a bug: a Context text sent to the chronological command, or a Context page outside 1 to 10) and `search_context_unavailable` (a 400 from `/search/smart` although `smartSearch` was reported on) and `search_context_service_unavailable` (any 5xx from `/search/smart`, which Immich answers when its machine-learning service is unreachable; this replaces `search_unavailable` for that endpoint only). `request_failure_code("search", ...)` maps the three status codes. `classifyFailure` in `search-controller.svelte.ts` turns the codes into `SearchFailure`: it special-cases `search_authentication_required` (a rejected key asks to sign in again, unlike the other sections, where the shared classifier makes it "unavailable") `search_context_unavailable` and `search_context_service_unavailable` (distinct states with their own messages that leave the Search Mode alone), and hands the rest to `classifyRequestFailure(reason, "search")` (permission denied, unavailable, otherwise a generic "unreadable response"). An unsupported server (`search_unsupported` with the required and the detected version) is a state of its own, not an error. A failed first load with results on screen is the offline state: the previous query and results stay visible with Retry. A failed further Context page keeps the pages already shown and offers Retry. Suggestion, city and people failures stay inside their own filter and never fail the Search.

#### Session state, Back and results

- **Session state**: the text, Search Mode, Search Filters, the loaded features and the Search Results live in memory in the Search controller only. They are reset by the clear control and by sign-out (`session-controller.svelte.ts` clears the controller, `+page.svelte` resets the origin) and are never persisted. Context is the default Search Mode; it falls back to Filename when Smart Search is off, and OCR to Filename when OCR is off. Features that arrive after a clear are discarded.
- **Back origin**: `+page.svelte` holds `searchOrigin = { view, top }`, the view the Search was started from (any view, including sub-views such as an Album Timeline) and its scroll position, recorded the first time a Search is submitted outside the `search` view. Refining from the results keeps the original origin. Back (`search_return` label) and the clear control return there; timeline views restore `top` through `scrollRestore`, other views through the content scroll position; Trash is refreshed and Explore refreshes if stale on return. The Archived option's "Open Archive" link switches to the Archive view like its navigation entry, with no Back button, and keeps the Search in memory.
- **Two result presentations**: **chronological** (every Search except one with a Context text): the controller is itself the timeline (Timeline Buckets by local month, Scrubber, at most the 5 000 newest, a notice when cut) and the notice is `truncated`; **relevance** (Context text): `context-results-controller` exposes one pseudo-bucket (`RELEVANCE_BUCKET`) in the Immich ranking order, 100 per page, further pages loaded while scrolling, no Scrubber, and a notice when the 1 000 limit was reached (`truncated` too). A Search that switches presentation clears the other one's results once the new Search has loaded; if it fails offline, the earlier results stay visible and marked offline, and Retry repeats the new Search (`search.results` is what the view shows, `presentation` stays that of the shown results until then). Both reuse the shared `TimelineView`, Lightbox and Remote Asset actions (Favorite, Download, Add to Album).

#### Permissions

`asset.read` is needed for every Search call; the Recognized People filter additionally needs `person.read` and the Tag filter `tag.read` (a key without one disables only that filter and names the permission; the Search itself still works); thumbnails and the Lightbox need `asset.view`. The Search itself never needs `tag.read`.

#### Verified on live server v3.4.1

Checked on 2026-11-17 by scripted read-only requests (`POST search/metadata`, `POST search/smart`, `GET search/suggestions`, `GET search/cities`, `GET server/features`, `GET server/version`, `GET people`, `GET tags`, `GET albums`) against a local throwaway Immich **v3.4.1** (official Docker compose, `D:\Development\immich-live-check`, seven generated 100-pixel JPEGs: three of them trashed, two archived, two favorites, none rated, none with camera, location, description or recognized text, no people, no Tags, no Albums, and the machine-learning service not running). Nothing was created, edited or deleted. "Source" means read from the server code in the v3.4.1 container image, not observed behaviour. Lymic's tests use a fake server that returns the shapes seen here.

| Assumption | Status | Observed outcome |
| --- | --- | --- |
| Context is Immich's default Search Mode. | CONFIRMED (source) | The Immich web client bundled in the v3.4.1 image starts every search in "smart" unless the user stored another type, and a typed text with that type is the smart search `query`. Not observable through the API. |
| `filter` is accepted and flat fields cannot be mixed with it. | CONFIRMED (v3.4.1) | `filter` works on `search/metadata` and `search/smart`. `city` or `page` next to `filter` is a 400 "Deprecated field ... cannot be combined with filter". |
| The structured `filter` needs Immich 3.2 (cut-off). | NOT VERIFIED | Only 3.4.1 was available. The v3.4.1 OpenAPI spec marks the flat fields "Deprecated v3.2.0", which is the only evidence. `/server/version` answers `{major, minor, patch, prerelease, featureLevel}`; Lymic reads major, minor and patch. |
| Metadata paging: `cursor` / `nextCursor`, `size` up to 1 000. | CONFIRMED (v3.4.1) | `nextCursor` is an opaque string (base64 of `{"offset":n}`), `null` on the last page; a bad cursor is a 400; `size` 1001 is a 400. `total` and `count` are the size of the page, not of the result. |
| Smart search pages with `page`, `size` and `nextPage`. | REFUTED, fixed | `page` with `filter` is a 400, which Lymic showed as "Context unavailable". The structured smart search takes only `size` (1 to 1 000) and (source) answers with `nextPage: null` and no cursor. Fixed: see [Search](#search) and ADR-0009. A successful smart response was not observed (no machine-learning service: the request validates, then answers 500 "Failed to search smart"). |
| Smart search applies the filters before ranking. | CONFIRMED (source), not observed | The structured smart query filters in its `WHERE` clause, joins the embeddings and orders by cosine distance with `LIMIT`, so the best results among the filtered assets are returned. How the vector index behaves with a very selective filter was not observed. |
| `takenAt` takes `gte` / `lte` instants. | CONFIRMED (v3.4.1) | Both bounds are inclusive and compared as instants (an asset taken at 12:00:00Z matched `gte 12:00:00.000Z` and `lte 12:00:00.000Z`, not `gte 12:00:01Z`); a `+02:00` offset is accepted; an empty `takenAt` object is a 400 (Lymic never sends one). The library has no time zone data, so local day versus UTC capture time was not distinguished. |
| `personIds: { all }` means every chosen person appears. | CONFIRMED (source), not observed | An unknown id is accepted and matches nothing; `all: []` is a 400 (Lymic omits it). The server counts the distinct people among the visible faces of an asset and requires all of them. The library has no people. |
| `tagIds: { all }` semantics. | NOT VERIFIED | The Tag filter sends it (#227). The condition is accepted by the server, but the test library had no Tags, so "every chosen Tag is on the Remote Asset" and "a child Tag does not count for its parent" were not observed. This is the structured search filter's `tagIds`, not the deprecated metadata-search `tagIds` and not the timeline's `tagId`. A key without `tag.read` was not tried against the Search either (the tree request is the one that fails). |
| Rating `eq` is exact; unrated assets. | PARTLY CONFIRMED (v3.4.1) | `rating: { eq: 3 }` matches nothing among the unrated assets, `eq: null` matches exactly them; 0 and 6 are accepted without error. Source: `eq` is a plain equality on the rating column. No rated asset existed to see an exact positive match. |
| Case sensitivity of `like`. | CONFIRMED (v3.4.1): insensitive | `like` on file name and path ignores case (`%A3%` and `%.JPG` match `a3.jpg`, an upper-case path matches). `eq` on the file name is case-sensitive. Source: `like` is `f_unaccent(col) ilike ('%' || f_unaccent(value) || '%')`, so it is also **accent-insensitive** (`%à3%` matched `a3.jpg`, confirmed) and always means "contains". The description column uses the same predicate (no description existed to observe it). |
| Backslash escaping of `%` and `_`. | PARTLY CONFIRMED (v3.4.1) | Unescaped `%` and `_` are wildcards (`a_.jpg` and `a%.jpg` match `a3.jpg`). A backslash neutralizes them (`a\_.jpg` and `%\%%` match nothing) and a dangling or doubled backslash is no error. That an escaped character matches the literal character was not observed: no name contained `_`, `%` or a backslash. |
| `visibility` default and the Archived option. | REFUTED default, confirmed option | Without `visibility` archived assets are **included**, so Lymic must send it (it does). `visibility eq archive` returns the same set as the Archive Timeline (the one archived live asset); `visibility eq timeline` leaves it out. |
| Trashed Assets are left out by default. | REFUTED, fixed | The structured `filter` returns trashed assets unless asked not to (the flat search and the timeline calls hid them). Fixed: every Search sends `trashedAt: { eq: null }`, which leaves exactly the live assets; see ADR-0008. |
| `hasAlbums: { eq: false }` selects Unfiled Assets. | PARTLY CONFIRMED (v3.4.1) | Accepted; with no Albums in the library `eq false` returns every live asset and `eq true` none. Source: `not exists (select from album_asset)`. No asset was in an Album to see a positive exclusion. |
| `ocr: { matches }`. | PARTLY CONFIRMED (v3.4.1) | Accepted with any text (also `100%_a`); matches nothing in a library without recognized text. Source: word-similarity on the tokenized text, so no wildcards to escape. |
| `country`, `state`, `city`, `make`, `model`, `lensModel` `eq` versus the suggested values (case, whitespace). | NOT VERIFIED | The conditions are accepted, are plain equality on the EXIF columns (source) and `eq: null` matches assets without the value. The library has no camera or location data, so every suggestion list was empty and no value could be compared. |
| Suggestion requests. | PARTLY CONFIRMED (v3.4.1) | All six types (including `city`, which Lymic does not use) and the `make`, `country` and `state` narrowing parameters are accepted and answered `[]`; an unknown type is a 400. Whether narrowing filters as assumed was not observed. |
| API key permissions. | PARTLY CONFIRMED (v3.4.1) | A key with only `asset.read` and `asset.view` can run `search/metadata`, suggestions, `search/cities`, `server/features` and `server/version` and reaches `search/smart` validation; `GET /people` is a 403 "Missing required permission: person.read". A bad key is a 401 "Invalid API key". A key lacking `asset.read` could not be tested without creating one. |
| `features.smartSearch` means Context can run. | REFUTED as a guarantee | The flag was `true` although the machine-learning service was unreachable; `search/smart` then answers 500, which Lymic shows as a Context-specific message about the machine-learning service (not "Context unavailable", which is for a 400, and not the generic "unavailable"). |

Not observed and still open: the 3.2 cut-off on a 3.2 server, `like` escaping of literal `%`, `_` and backslash in real names, case and whitespace of camera and location values, Rating on rated assets, `hasAlbums` on assets in Albums, `personIds` and `tagIds` `all` against real people and Tags, OCR text matching, a successful smart search response (including that filters rank before the limit), and a key lacking `asset.read`. To re-run the check on another server or release: prepare assets with camera and location EXIF, a description, a Rating, one Album, one Recognized Person with two faces, a Tag and a running machine-learning service, replay the requests above with `curl -H "x-api-key: <key>"`, record the result and the Immich version here, and open an issue for anything that differs.
