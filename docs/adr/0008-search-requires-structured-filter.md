# ADR-0008: Search requires Immich 3.2 and sends only the structured filter

Lymic's Search combines many Search Filters (Recognized Persons, dates, Location, Tags, media type, camera, Rating, Favorite, Archived Asset, Unfiled Asset) with an optional text. Immich 3.2 introduced a structured `filter` object on its metadata and smart search endpoints: filters combine at the top level, people and tags take `any`, `all` or `none`, and a Remote Asset's absence from every Album is `hasAlbums: { eq: false }`. Immich marks the older flat fields (`personIds`, `city`, `takenAfter`, `rating`, `isNotInAlbum` and the rest) as deprecated, and a request that mixes flat fields with `filter`, `orderBy` or `cursor` is rejected. Lymic's Search therefore requires Immich 3.2 or later and sends only the structured `filter`. Before the first Search it reads the server's version and features; an older server shows the Search as unsupported, with the required version, and leaves every other view untouched.

## Considered Options

- **Support both request shapes**: Rejected because every Search Filter would be built, tested and verified twice, and the two shapes differ in meaning (`all` on people and tags, `hasAlbums`, `trashedAt` and `like` on the file name, path and description exist only in the structured shape, and the same meaning differs between the shapes: the flat fields hid trashed Remote Assets, the structured `filter` does not).
- **Send only the flat fields**: Rejected because Immich has deprecated them and has no structured replacement for several combinations Lymic needs (`all` on people and tags).
- **Probe by trying the structured request and falling back on a 400**: Rejected because a fallback would hide the real reason a request failed and send credentials-bearing requests twice.

## Consequences

- The Search is unavailable on Immich servers older than 3.2. No other view is affected, because Photo Timeline, Album Timeline, Place Timeline and Explore keep their current requests.
- Album Timelines and Place Timelines still send the flat `albumIds` and `city` fields (ADR-0006, ADR-0007). They keep working while Immich accepts the deprecated fields. Moving them to the structured `filter` is possible once the minimum version applies to them, but is not part of introducing Search.
- The 3.2 cut-off comes from Immich's source annotations ("v3.2+") and the `Deprecated v3.2.0` marks in the OpenAPI spec. It was not tested against a running 3.2 server: the live verification (2026-11-17, [application map](../agents/application-map.md#search)) ran against 3.4.1 only and should be repeated on a 3.2 server and on the first later release.
- Every Search sends `visibility` explicitly and `trashedAt: { eq: null }`. Verified on 3.4.1: without `visibility` the structured search returns Archived Assets, and without `trashedAt` it returns trashed Remote Assets, which the flat fields and the timeline endpoints leave out by default. The Archived option (`visibility: archive`) returns the same Remote Assets as the Archive Timeline.
- Verified on 3.4.1: `like` on file name, path and description means "contains" (Immich wraps the value in `%` itself), ignores case and accents, and treats `%` and `_` as wildcards that a backslash neutralizes. `eq` is case-sensitive. Lymic's own `%` wrapping is redundant but harmless and was kept.
- Verified on 3.4.1: `takenAt` bounds are inclusive instants; `rating: { eq: n }` does not match unrated Remote Assets; `personIds: { all }` is "every chosen person appears" (from the server code); unknown ids match nothing.
- Still unverified against a live server (the test library had no data for them): case and whitespace of the camera and Location values against the suggestions, Rating on rated Remote Assets, `hasAlbums` on filed Remote Assets, `personIds` and `tagIds` `all` with real people and Tags, literal matching of escaped `%`, `_` and backslash, OCR matching, and a key lacking `asset.read`.
- Context and OCR Search Modes also depend on the server features `smartSearch` and `ocr`, read from `GET /api/server/features`; a disabled feature disables only that Search Mode.
- Search needs the API key permission `asset.read`. The Person Search Filter additionally needs `person.read`, and the Tag Search Filter will need `tag.read` once it is delivered (it waits for Tags to become readable, #227); a key lacking one disables only that filter.
- The Search never mutates a Remote Asset, so it requires no write permission.
